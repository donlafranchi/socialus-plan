# SocialUs URL plan: one address per thing, the ID resolves

*Researched 2026-10-06 against socialus-web and socialus-plan main, plus a read-only look at the production database.*

## Summary
**Rule (extends the 2026-09-21 ruling to everything):** each public thing has one short random ID, and only the ID resolves. The URL carries no geography, member or parent hierarchy. Exactly one route renders each thing; every other shape permanently redirects to it.

| Thing | Recommended URL | Today |
|---|---|---|
| Page | socialus.org/g/tzsxja | /g/the-good-loaf-tzsxja |
| Post (announcement, event; later product/service) | socialus.org/p/4k7q9m2x | no URL of its own; /g/…#announcement-<uuid> |
| Place | socialus.org/places/ca/sacramento/oak-park | /p/ca/sacramento/oak-park |
| Location ("venue") | retired: redirects to the hosting Page | /p/<place>/l/<slug> |
| Member (future) | nothing built; /u/ and /@ reserved | none (You is private); items without a Page use /m/<handle>/e/<title>-<id8> |
| App screens | unchanged | same |

**Findings:** (1) The rename bug isn't a URL bug: the Page reads its name from the business record, but Edit writes groups.name. (2) Single posts have no URL; a shared post previews as its Page. (3) Member handles are in public URLs today: 12 of 16 published items have no Page and live at /m/<handle>/…, and a public lookup (posted_item_id) confirms which items a handle posted, which breaks the 2026-09-21 safety ruling. No new ones can be created (composers unrouted since #336). (4) Every shared link previews as plain "SocialUs": Open Graph is only set at the root layout (read from code, not tested).

**Before beta:** fix the name source; switch the Page canonical address (decision 1); freeze groups.slug so old links keep resolving; record the ruling. Everything else before production.

## 1. Current state, verified
- Page /g/[handle]: resolves by the 6-char Crockford ID, falls back to whole-handle slug, non-canonical forms permanently redirect (resolve-page-address.ts). Slug never regenerated on rename; business name in two columns.
- Old Page paths /p/<place>/g/<slug>: permanent redirect to /g/… (fine).
- Items /p/<place>/g/<slug>/e|p|s/<title>-<id8>: look up the Page by slug, match the item's UUID prefix in app code; place segments never checked. Breaks if the slug changes. Products resolve only on business Pages.
- Items without a Page /m/<handle>/e|p|s/…: member identity in the URL.
- /m/<handle>: 404 to everyone, redirects the member to You (#303).
- Posts (page_posts, 11 rows): fragment only (announcement-anchor.ts anticipates a real URL).
- Venue /p/<place>/l/<slug>: global slug lookup ignoring place segments; any prefix renders it (the duplicate-address defect #175 fixed for Pages).
- Place /p/ca/sacramento/oak-park: renders a placeholder with developer text on production.
- Metadata: titles/descriptions per page; Open Graph only at root; no metadataBase; no canonical tags.
Verified: code paths, production counts (10 active Pages, 16 published items, 12 without a Page, 11 posts, 11 locations, 265 places). Assumed: share-preview behaviour. Not found: ADR-20 and ADR-0022 files (read via code comments).

## 2. The scheme, and why
- ID resolves, words don't (already the Page ruling; applied everywhere). Random Crockford base32, lower-case, case-insensitive. Pages 6 chars, posts 8. Any slug + right ID redirects to canonical. No slug-history table (ruled out 2026-09-21).
- One prefix per noun, no nesting: /g/<id> Page, /p/<id> post. A post's kind isn't in its URL (a post can gain a date and become an event). Precedent: Instagram /p/<code> for all post types; Airbnb /rooms/<id> per listing whoever owns it, host at /users/show/<id> (noindex).
- Places are indexes, not homes (§4).
- No new tools: socialus.org/g/tzsxja is 23 characters.

## 3. Precedents
- ID-only: Airbnb /rooms/<id> (https://community.sabeeapp.com/discussions/post/how-to-find-your-airbnb-host-id-LUJJLmrmgJ8RdF2); Instagram /p/<shortcode> (https://developers.facebook.com/documentation/instagram-platform/oembed).
- Slug + ID: Stack Overflow /questions/<id>/<slug> (https://blog.jim-nielsen.com/2023/examples-of-great-urls/); Etsy /listing/<id>/<slug>, shop renames redirect (https://help.etsy.com/hc/en-gb/articles/115015710568-How-to-Change-Your-Shop-Name); Discourse id + slug (https://meta.discourse.org/t/how-do-url-topic-title-updates-work/83633).
- Name as identity (cautionary): YouTube old handles redirect 14 days then are claimable (https://support.google.com/youtube/answer/15920820); Facebook username change invalidates old URL (https://www.socialpilot.co/de/facebook-marketing/change-facebook-url); Meetup group URL is the name, never reusable (https://help.meetup.com/hc/en-us/articles/360002861772-Changing-a-group-s-URL); Yelp /biz/<name>-<city>-2 (https://docs.dataforseo.com/v3/business_data/yelp/overview/).
- Place pages: Nextdoor, Meetup /cities/us/ca/<city>/, Yelp city search: discovery landing, not a home (observed, not confirmed against docs).
- Redirects/SEO: https://developers.google.com/search/docs/crawling-indexing/301-redirects, https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls, https://developers.google.com/search/docs/crawling-indexing/url-structure. 301 and 308 both pass signals; readable words help a little (the real cost of ID-only).
- Share previews: https://ogp.me/, https://nextjs.org/docs/app/api-reference/functions/generate-metadata.

## 4. Place URLs: what they're for
Recommendation: keep the place tree, keep place URLs as index pages, move them to /places/…, build nothing more until production. Originally places were part of every address; the 2026-09-21 ruling took them out of identity. Internally they still drive "near me", Explore's area lens and the Locally owned MSA test (data, not URLs). Publicly they're discovery landing pages. The PM's local-pride scoreboard idea (communities competing to keep spending local) fits a place page later, but needs Purchase, which isn't tracked yet. Now: noindex the placeholder or redirect it to Explore filtered to that place.

## 5. Redirects and migration
Every old shape keeps working (permanentRedirect = 308).
- /g/<slug>-<id> → /g/<id> (already resolves by ID).
- /g/<slug> → /g/<id> (existing fallback).
- /p/<place>/g/<slug> → /g/<id> (exists).
- /p/<place>/g/<slug>/e|p|s/<title>-<id8> → /p/<postid> (requires groups.slug frozen).
- /m/<handle>/e|p|s/<title>-<id8> → /p/<postid>, ignoring the handle (closes the lookup leak).
- /g/<id>#announcement-<uuid> → /p/<postid> (tiny client-side redirect, kept forever).
- /p/<place>/l/<slug> → owning Page /g/<id> (or the place).
- /p/ca/sacramento/… → /places/ca/sacramento/… (2-letter state vs 8-char post id can't collide).
Canonical/OG: metadataBase; alternates.canonical and og:url per page; own og:title, og:description, og:image. Pick one host (robots.ts assumes www, links say apex) and permanently redirect the other in Vercel (free). Sitemap of /g/ and /places/ when production SEO is in scope.

## 6. Beta cut
Before beta (~1 day): name source fix; canonical Page address per decision 1; freeze groups.slug; record the ruling (DECISIONS.md + planning/URL-IDENTITY.md).
Before production: post IDs and /p/<id>; places to /places/; retire Location pages; item and fragment redirects incl. closing handle-based item URLs; canonical + OG tags; host canonical and sitemap.
Scope-creep flags (not beta): place landing pages or scoreboard; a short domain; vanity Page handles; slug-history table.
Risk: the 12 handle-carrying items stay live through beta; tolerable only because none can be created and there are no real members yet.
